## Договор правил

| Элемент | Реальная реализация / проверка |
|---|---|
| Набор / раздача | Double-six, 28, по 7; сохранение набора проверено симуляциями |
| Начало Telefon | Приоритет 3–2, затем минимальный дубль от 1–1, 0–0, fallback |
| Стартовые очки | 5–5 даёт 10 с ограничением контекста текущих очков |
| Телефон / открытые концы | Общий board core и клиентская копия; parity на каждом ходе |
| Базар / pass | Telefon и 101 маршрутизируются через ruleset; видимость кнопок имеет устаревший статический тест |
| Гоша / плохая стартовая рука | 691 гоша в полных матчах; seed225 выявил R-32 при старте 101 |
| Рыба | R-31: сервер 101 теряет matchState; реальный fixture79→129 остаётся 79 |
| Telefon match | Target365 или instant win; roundWins1/2 не означает автоматически best-of-three |
| Classic101 | Положительное накопление до 101, старт 1–1, порог входа 13 и перенос при ничьей в ruleset; это выбранный региональный вариант |
| 2v2 | Командные суммы и отдельные winners; нужен согласованный набор примеров владельца |

Не следует заменять 101 вариантом, где достижение 101 означает поражение: одинаковое название не означает одинаковый договор правил. Для каждого режима показывать краткую карточку до матча и сохранять `rulesetVersion` в результате.

## Подтверждённый дефект R-08

`shared/domino-rulesets.cjs:100` читает `state.instantWinEnabled`, а `js/app.js:19894,19973` и `server/DominoRoom.js:3489,3658` передают `isInstantWinEnabled`. При score 35 выключенный switch всё равно даёт instant win. Доказательство — `disabledInstantWinStillWins: true` в [game-simulation.json](evidence/metrics/game-simulation.json).

Минимальное исправление: единое имя параметра, typed contract и тест `true/false/undefined × score 30/35/40` для клиента и сервера. Проверить назначение двух выигранных раундов и отсутствие двойного settlement. Риск исправления — изменение результата уже привычной пользователям партии; явно указать в release notes.

## Серверная авторитетность

`handlePlay/draw/pass/gosha` работает с серверными руками, очередью и board, а не принимает клиентские scores как истину. Full state содержит `selfHand`, а не все чужие руки (`DominoRoom.js:2733`). Это правильная основа. Пробел — ownership при restore: авторитетная симуляция бесполезна, если атакующий получает чужое место. Подписанные результаты проверяются API, но резерву нужна жёсткая связь с matchId.

Для усиления: turnId и commandId; дедупликация повторных команд; reject устаревшего хода с новым snapshot; replay log без раскрытия чужих рук; server-side match finality. Клиентский optimistic rollback обязан приводить к серверной версии состояния.

## Боты

Три сложности отличаются весами немедленного score, выхода, оставшихся очков, будущих возможностей и случайности. Это лёгкие эвристики, тяжёлые модели не нужны. Среднее число шагов в исследованных раздачах — около 19–27 в зависимости от режима и состава; wall-clock время партии не измерялось.

`server/ai.js:101–125` в teamContext проверяет фактические костяшки партнёра и соперников. В `DominoRoom.js:2502` контекст подаётся для командного takeover. В paired-world probe при неизменных публичном поле и собственной руке оценка хода меняется только из-за другой скрытой руки партнёра: [bot-hidden-info.json](evidence/metrics/bot-hidden-info.json). Это подтверждённое информационное преимущество; обычным solo-ботам такое поведение автоматически не приписывается.

Честная замена: передавать число чужих костяшек, историю открытых ходов, известные пропуски и вероятностные оценки. Лёгкий бот иногда выбирает второй допустимый ход; средний использует greedy + hand shape; сильный — ограниченный rollout по возможным скрытым рукам, не настоящим. В интерфейсе обозначать AI и замену отключившегося игрока.

Результаты `winsByDifficulty` первоначального JSON — число выходов, не population win rate. В трёх местах сложности повторяются у разных участников; рыба исключена из этих счётчиков. В продолжении выполнен paired-seed tournament:960 матчей, интервалы по 80seed-парам на комбинацию. [Результаты](CONTINUATION_ANALYSIS.md) не дают убедительного разделения medium/hard вTelefon;101 надо перепроверить после R-31. Длительность живых партий и стратегические ошибки через независимый oracle остаются открытыми. Не использовать эти цифры как win rate против людей.
