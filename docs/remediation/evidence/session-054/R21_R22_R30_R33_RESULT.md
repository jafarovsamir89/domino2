## Проверки R21 и незакрытый объём

Новый аддитивный SQL20, AccountDeletionService/Controller/явно составляемый Module, DatabaseAccountErasure и отдельный fsynced AccountErasureJournal. Подтверждение HMAC привязано к действию, аккаунту, сессии и версии удаления на 10 минут. Нельзя передать чужой ID в теле запроса, отменить входом или повторить старое подтверждение после отмены. Выполнение/восстановление блокируется при неполном составе обработчиков.

Свежая локальная база `_deletion_6` и отдельная `_restore_6`: настоящий Nest HTTP + AuthService + PostgreSQL + pg_dump/psql. **Это не подмена SQL-бэкапа объектом в памяти.** Проверены 401/403/400, отзыв всех сессий, повторный вход без отмены, явная отмена, точная 30-дневная граница, сохранение стартовой награды, запрет игрового доступа, блокировка при незакрытом резерве и ошибке/неполном ответе внешнего обработчика. При ошибке аккаунт остаётся закрытым и сохраняется для повтора. После успешного удаления проверка 41 модели не находит личных строк синтетического владельца; чужой кошелёк сохранён. Данные победителя у другого участника теперь также обезличиваются: отдельный red `deletion-shared-red.txt`, затем green `deletion-final-db.json`.

Старый настоящий SQL-бэкап восстановлен в другую свежую БД. До повторного удаления допуск блокируется; журнал повторно удаляет аккаунт, затем допускает запуск. Наличие покрываемой SQL-копии на 60-й день блокирует удаление маркера, после явной очистки тестовой копии маркер удаляется. Каталог журнала должен иметь уже существующий persistent-volume parent; создание каталога/файлов синхронизируется на диск. Маркеры не содержат имени, почты или токенов. Завершённая запись в БД очищает userId/playerId, чтобы новые SQL-копии не продлевали их хранение.

Страница удаления показывает новую политику и действия **только** при точном доступном контракте сервера. Старый backend сохраняет прежний mailto-путь. В новом режиме старые английские/неоднозначные разделы скрываются; используются AZ/RU/EN, типизированное DELETE, новый вход для отмены и очистка ввода при смене аккаунта. Native WebView отправляет пользователя на канонический сайт без локального OAuth/удаления. Последний набор страницы — **9/9**, `deletion-page-final.txt`; реальный Google OAuth ещё не проверен.

**Осталось реализовать:** настоящий адаптер Redis/живых комнат/закрытого settlement-outbox; удаление или подтверждение отсутствия данных у фактически включённых обработчиков; управление всеми покрываемыми бэкапами и постоянным журналом; доставка уведомления об ошибке; полная runtime-композиция с restore gate до допуска запросов. Module намеренно не импортирован в production AppModule. Нельзя включать его одним флагом или заменить адаптеры синтетическими подтверждениями.

Финансовые idempotency/reference-ключи сохранённых чужих расчётов не переписываются; некоторые могут содержать непрямую ссылку на старый ID. Их минимизацию/сроки хранения ещё нужно отдельно проверить; нулевой scan личных строк не доказывает отсутствие каждого непрямого идентификатора.

Реальные платежи, незавершённые расчёты, активные турниры и staff-аудит блокируют уничтожение, а не исчезают по таймеру. Срок обязательного хранения платёжных/модерационных данных отдельно не утверждён. Нельзя обещать безусловное удаление всего на 30-й день при этих исключениях. ## R30 — права и Data Safety

Реестр: **154 пути / 88 разных хешей / 0 неподтверждённых записей** по принятому основанию: собственные материалы — заявление владельца «сделали сами»; сторонние — конкретные источники и лицензии. Это не независимая экспертиза авторства. Десять реакций — OpenMoji CC-BY-SA4, одна из версии15.1.0; ошибочно приписывать их собственному авторству нельзя. Добавлены полные уведомления, third-party.html и ссылка в профиле. Подтверждены конкретные байты Konva/Socket.IO, происхождение Colyseus/GSAP; лицензия schema4.0.13 дополнительно проверена по npm integrity, Inter — по официальному OFL. Нормализация CRLF лицензии не меняет её условий.

Настоящая Play Console: все 13 типов помечены collected/not shared/ephemeral/required. Хранимые аккаунт и переписка не являются только временной обработкой. Использование имени/почты/голосовых сообщений для рекламы кодом не подтверждается. Ответ «удаление отдельных данных без удаления аккаунта — да» не соответствует проверенному процессу. Подробности и оставшиеся проверки — [PLAY_DATA_SAFETY_REVIEW.md](PLAY_DATA_SAFETY_REVIEW.md). По завершении read-only осмотра Console явно показала отсутствие неопубликованных изменений.

Нужно сверить актуальные Sentry/FCM, логи/геолокацию/поиск, условия обработки провайдерами и фактическое хранение. В частности, FCM может инициализироваться через стандартные credentials, а не отдельный флаг; отсутствие ключа в локальной конфигурации не доказывает отсутствие провайдера на сервере. Код push передаёт токен устройства и имя отправителя. Privacy сейчас заявляет до90дней диагностики, что надо согласовать с общей политикой удаления/копий и реальным хранилищем. При будущей подготовке анкеты использовать конкретную конфигурацию релиза, а не гипотетическую рекламу.

## Следующий шаг

R21: начать с реального игрового адаптера и его отрицательных проверок — активная комната, недоступный Redis и нерассчитанный outbox должны блокировать стирание; никакого удаления расчёта другого игрока. Затем retention/processor adapters, уведомления и общая runtime/restore-приёмка. Параллельно владелец проверяет слова; R30 уточняется по фактическим сервисам. Только затем согласовывать сохранение готовой анкеты и отдельный deployment/release. Секреты, production-данные и `.env` в доказательства не включены.


До будущего deployment: аддитивная migration20 должна быть применена перед API, который выбирает новые поля Player. После принятия первых запросов удаления нельзя просто откатиться на старый API, игнорирующий pending-marker/restore gate: это вернёт доступ закрытым аккаунтам. Нужен проверенный совместимый rollback. Этот шаг также не выполнялся на production.
