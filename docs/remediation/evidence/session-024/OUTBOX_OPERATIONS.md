# R-29 — локальная приёмка и требования к последующему выпуску

До HTTP-запроса paid-result записывается неизменяемый intent: roomId/matchId/stakeKey/result/winnerUserIds. Запись синхронно fsync, публикация hard-link без перезаписи, fsync каталога; callback сети вызывается только после этого. Конфликт результата для того же матча не заменяет первый intent. После подтверждённого `ok:true` отдельным fsync сохраняется receipt. Неподтверждённые и повреждённые записи не удаляются. Повторная доставка использует существующую транзакционную защиту exact match из R-03. Ответ skipped при reconciliation допустим только при наличии exact room/match/stake записи начисления в ledger; неизвестная ставка/резерв не подтверждают доставку.

Фоновый worker запускается вместе с game server и каждые5с выбирает до32 pending-записей. Одновременно идёт один проход, каждый HTTP имеет5с deadline, очередь циклическая: постоянный отказ не блокирует следующие записи навсегда. Восстановление одного результата может ждать очередь; это не обещание доставки за5с при любом backlog. Нет зависимости от живой комнаты, срока bearer-токена или logout пользователя: отдельный API endpoint принимает только подписанный сервером scope `economy.reconcile`. Обычный settle endpoint по-прежнему требует действительный игровой токен и свой scope. Клиент не получает серверный секрет.

## Перед будущим развёртыванием

- Настроить `ECONOMY_OUTBOX_DIR` как абсолютный путь на **постоянном локальном томе**. Production без этого пути не стартует. API с новым endpoint должен быть выпущен раньше game server. Старый API будет отклонять replay; intent останется на диске.
- Том должен переживать restart/replacement контейнера и откаты версии. Для нескольких реплик каждая должна сохранить и повторно подключить свой том; нельзя просто удалить старую реплику вместе с её pending intents. Общий сетевой filesystem без проверки fsync/link semantics этим тестом не принят.
- Каталог0700, файлы0600. Не публиковать его через www, не включать в Git/образы. В нём есть user IDs, денежные итоги и receipts; bearer-токены туда не пишутся. Нужны backup, мониторинг свободного места, pending/ошибок и согласованная политика хранения завершённых записей. Автоматического удаления финансовых записей в этой правке нет.
- Ошибка записи закрывает отправку результата и оставляет комнатную попытку pending. Неисправный диск требует восстановления/оператора; очередь не защищает от физической потери тома, повреждения всего хранилища или kill до вычисления/сохранения итога.
- Runtime recovery касается **денежного settlement**. Повторная рассылка утраченного UI-события и отдельная запись статистики матча не становятся гарантированными автоматически. После response loss API может вернуть `skipped:true`; баланс корректен, но полный первоначальный receipt может отсутствовать. Обычный room retry продолжает работать, а новый матч защищён от старого callback.

Все действия этой сессии выполнялись на localhost с синтетическими пользователями/кошельками. Ни production, ни версия Play не изменены. Docker/сервер на рабочей машине не запускались против production.

Реализация использует доступные в Node22 fsync/link и AbortSignal.timeout: [Node fs](https://nodejs.org/docs/latest-v22.x/api/fs.html), [Node AbortSignal](https://nodejs.org/docs/latest-v22.x/api/globals.html#static-method-abortsignaltimeoutdelay). Это не гарантия аппаратной сохранности диска.
